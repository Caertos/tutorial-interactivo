Cómo viaja una petición web, de punta a punta

GET /libros/7

Haces clic en «Ver libro». Seguimos ese clic por la red, el servidor y la base de datos, y de vuelta hasta el HTML pintado: qué hace cada capa y con qué forma viaja el dato.

Stack de los ejemplos: Google Chrome · Node.js 26 con Express 5.2 · SQLite (node:sqlite).

Suposiciones: una biblioteca inventada en biblioteca.ejemplo; conexión HTTPS con TLS 1.3; la petición se muestra como texto HTTP/1.1 (HTTP/2 y 3 envían los mismos campos en binario). Todas las respuestas y filas salen de ejecuciones reales.

Avanza con → o Espacio, desliza en el móvil o toca «Siguiente».

El viaje completo

Seis capas, diez saltos. Mira cómo cambia la forma del dato: texto HTTP, parámetros, SQL, filas, objeto, HTML y, al final, píxeles.

El clic se convierte en petición

Un enlace no «llama a una API»: le dice al navegador que pida un documento nuevo.

<a href="/libros/7">Ver libro</a>
GET /libros/7 HTTP/1.1
Host: biblioteca.ejemplo
Accept: text/html,application/xhtml+xml,…
Accept-Language: es-419,es;q=0.9
Accept-Encoding: gzip, deflate, br, zstd
Referer: https://biblioteca.ejemplo/libros
Sec-Fetch-Mode: navigate
  • GET

    El método. Un enlace siempre pide con GET: leer, sin cambiar nada. Por eso no lleva cuerpo.

  • /libros/7

    La ruta. El navegador resuelve href contra la página actual; el 7 es el dato que seguiremos.

  • Host

    A qué sitio va. Un mismo servidor puede atender varios dominios.

  • Accept

    Qué formato prefiere: HTML. Un fetch() de datos pediría application/json.

  • Accept-Encoding

    Qué compresiones entiende, para que la respuesta pese menos.

  • Referer · Sec-Fetch-Mode

    De qué página vienes y que es una navegación. Son cabeceras reales que Chrome envió en la prueba.

Antes del primer byte

La petición aún no puede salir: falta saber a qué IP va y abrir una conexión cifrada.

Dentro del servidor

Cada capa tiene un trabajo: la ruta elige el código, el controlador traduce HTTP y el servicio habla con la base de datos.

import express from 'express';
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync('biblioteca.db');
const app = express();

// Service: business rule, knows nothing about HTTP
function obtenerLibro(id) {
  const sql = 'SELECT id, titulo, autor, anio FROM libros WHERE id = ?';
  return db.prepare(sql).get(id);
}

// Controller: HTTP in, HTML out
app.get('/libros/:id', (req, res) => {
  const libro = obtenerLibro(Number(req.params.id));
  if (!libro) return res.status(404).send('<h1>Libro no encontrado</h1>');
  res.send(paginaLibro(libro));
});
  • /libros/:id

    La ruta. :id es un comodín: /libros/7 encaja y Express llama a esta función con req y res.

  • Number(…)

    Todo lo que viene en la URL es texto. El controlador lo convierte antes de pasarlo.

  • obtenerLibro

    El servicio prepara la consulta con ? y pasa el valor aparte. .get() devuelve la primera fila como objeto o undefined.

  • 404

    Sin fila no hay libro: se responde «no encontrado» en vez de romper la plantilla.

  • res.send(html)

    paginaLibro() convierte el objeto en texto HTML; res.send lo envía con Content-Type: text/html.

La consulta y sus filas

SELECT id, titulo, autor, anio FROM libros WHERE id = 7 sobre una tabla de cinco libros.

Con /libros/99 la consulta devuelve 0 filas, .get() da undefined y el controlador responde 404.

La respuesta HTTP

Esta es la respuesta real que envió Express: una línea de estado, cabeceras, una línea en blanco y el cuerpo.

HTTP/1.1 200 OK
X-Powered-By: Express
Content-Type: text/html; charset=utf-8
Content-Length: 224
ETag: W/"e0-FHq62/VbOXoqY93mkz7X7+6xmvE"
Date: Mon, 19 Oct 2026 19:02:37 GMT

<!DOCTYPE html>
<html lang="es">
<head>
  <title>Rayuela</title>
  <link rel="stylesheet" href="/estilos.css">
</head>
<body>
  <h1>Rayuela</h1>
  <p>Julio Cortázar · 1963</p>
  <a href="/libros">Volver</a>
</body>
</html>
  • 200 OK

    El código de estado: 2xx salió bien, 3xx «mira en otro lado o usa tu copia», 4xx error de la petición (404), 5xx error del servidor (500).

  • Content-Type

    Cómo interpretar el cuerpo: como HTML y en UTF-8. Express lo puso solo al recibir un texto.

  • Content-Length

    El tamaño del cuerpo en bytes, para saber dónde termina.

  • ETag

    Una huella del contenido. En la próxima visita el navegador puede preguntar «¿sigue igual?» y recibir un 304 sin cuerpo.

  • cuerpo

    Tras la línea en blanco, el HTML que generó la plantilla. El dato ya no es una fila ni un objeto: es texto.

El navegador construye el DOM

El HTML es texto; para pintarlo, el navegador lo convierte en un árbol de nodos: el DOM.

Un <script> sin defer en head detendría el parseo hasta descargarse y ejecutarse.

SSR frente a CSR

La diferencia es quién escribe el HTML. Con SSR lo escribe el servidor y llega hecho. Con CSR el servidor envía una página casi vacía y el JavaScript del navegador la completa con JSON.

Mismo servicio y misma consulta en los dos casos: con SSR el controlador termina en res.send(paginaLibro(libro)); con CSR, en res.json(libro).

Cuánto espera cada uno

Medido en viajes de ida y vuelta, con la conexión ya abierta y sin contar CSS ni imágenes. Ilustrativo: no son milisegundos medidos.

CSR compensa en las navegaciones siguientes: app.js ya está cargado y cada pantalla nueva solo pide JSON.

Qué evitar

Sin cachéCada visita repite consulta y plantilla aunque el libro no cambie; el ETag solo ahorra bytes, porque el 304 se decide después de generar la página. Evítalo con Cache-Control: max-age=… o caché en el servidor o la CDN.

Lo que tendrás que decidir: qué pantallas necesitan aparecer rápido (SSR) y cuáles son muy interactivas (CSR), y qué respuestas puedes cachear.

En resumen

Ida

Clic → GET /libros/7 con cabeceras → DNS, TCP, TLS → Express elige la ruta → controlador → servicio → SELECT … WHERE id = ?.

Formas del dato

Texto HTTP → '7' → 7 → SQL → fila → objeto → HTML o JSON → DOM → píxeles.

Vuelta

200 OK + Content-Type + cuerpo. El navegador parsea, construye el DOM, espera el CSS y pinta.

SSR o CSR

SSR: el servidor escribe el HTML, un viaje. CSR: el servidor da JSON y el navegador escribe el HTML, más viajes la primera vez.

Cuidado con

N+1, falta de caché, errores SQL visibles, SQL concatenado y scripts que bloquean el render.
